## Consolidated findings and narrow repairs

**F1 — same-principal import/booking lock inversion (closure blocker; SAR-009, A-06).** Ordinary create locks user → asset → policy (`reservations/services.py::_lock_principal`, `create_reservation`). Import locks asset → user → policy (`legacy_import/importer.py::_revalidate_for_apply`, also `_create_imported_reservation`). The independent probe gates only after actual row locks, then releases the genuine second-lock acquisition: PostgreSQL aborts booking with **OperationalError SQLSTATE 40P01** while import commits one reservation/one audit. Existing import races use distinct mapped user/booker and therefore miss this cycle. This is not a data-overlap breach: exclusion and transactions preserve one reservation. It is an explicit consistent-lock-order violation and ordinary caller availability failure. There is no public import endpoint; triggering it requires the operator import path alongside ordinary booking. Real legacy migration remains D2/out-of-target, but preserved synthetic import and its concurrency contract were not deferred.

H/A/E/I/C repair linkage: H = selected preservation of shared PostgreSQL/domain guarantees; A = A-06 + SAR-009; E = current exact source plus `ICA_IMPORT_DEADLOCK` real-PG result; I = this fresh ICA F1; C = NONE (ordinary engineering repair, no new rights/judgment). A narrow corrective objective should reconcile lock acquisition across importer and existing create/cancel/release/blackout/policy paths, including batch ordering, and add same-principal barrier-controlled real PostgreSQL negative/recovery tests. Preserve policy/exclusion/audit semantics; do not authorize private migration or introduce silent retries hiding failures. Architecture-to-new-main ICA must revisit the whole matrix after merge.

**F2 — unrelated actual audit constraint error silently becomes a successful applied/conflict batch (closure blocker; SAR-007, SAR-029; A-06/A-11).** The disposable probe adds a temporary audit-table CHECK rejecting reservation.created, then calls real apply_import without mocking persistence/audit. The real audit INSERT fails; catch-all IntegrityError in `legacy_import/importer.py::apply_import` turns it into `reservation_conflict`, commits an APPLIED batch with imported 0/conflict 1/error 0, and returns normally. Reservation/import record/audit disappear via savepoint, but the applied batch persists. There was no conflicting reservation. Ordinary booking already translates only the named exclusion failure. This violates the explicit rule that unrelated integrity errors remain errors for investigation and the full-operation rollback/truthful final report contract.

H/A/E/I/C linkage: H = preserved integrity/audit/import reporting; A = SAR-007/SAR-029 and A-06/A-11; E = actual audit CHECK failure with `ICA_IMPORT_INTEGRITY` plus exact catch block; I = F2; C = NONE. A separate narrow correction should translate only validated expected consistency constraints, propagate all unrelated integrity/audit failures, roll back batch/domain/audit/import artifacts, and test real named exclusion, actual audit constraint failure and import-key races. No fabricated conflict or success report; no product scope expansion/private data.

**F3 — warm-cache Docker image metadata fails creation receipt and leaks its owned test image (closure blocker for complete qualification/resources; SAR-031; relevant SAR-045/032 evidence limit).** Canonical `tests/test_branding.py::_OwnedDocker.remember` treats image Created as creation-attempt time. Cold `--no-cache` builds pass the same canonical ownership checks and then the actual default/custom/read-only/no-rebuild/fallback assertions. This demonstrates a qualification/receipt flaw, not an application theming defect or a need to disable ownership protection. Full current CI runs on a fresh runner and does not exercise this warm-cache path.

H/A/E/I/C linkage: H = disposable ownership/no foreign deletion and real container branding qualification; A = SAR-031/A-10/A-15; E = two canonical cached refusals, `cached-image-receipt.json`, `cached-image-second-receipt.json`, successful cold result; I = F3; C = NONE. ## Gate recommendation and practical limits

The strongest concrete argument against treating this revision as Internet-deployment-ready is that full architecture closure would conceal demonstrated preserved import integrity/locking violations and an unreliable warm-cache qualification/cleanup path. The new Internet-facing controls, default policy, public entry, product identity, accessible forms, safe customization, visual design and threading have substantial independently inspected source/runtime/negative evidence. The import defects are operator-path defects, not proof of anonymous network compromise, and the cached-build failure is in qualification ownership, not the deployed theming handler. Those distinctions do not allow this auditor to waive the preserved rows or manufacture deferral authority.

Software evidence supports presenting this exact immutable revision and its candid findings for **human review**, but does **not** support presenting M-INTERNET-UX-PILOT as complete or recommending real exposure until the blockers are repaired/re-audited or explicitly scoped/deferred by appropriate human authority. No disposition is invented. Host hardening, actual proxy peer/topology, real certificate/domain/TLS lifecycle, firewall/public routing, real secrets/identity/account onboarding, broad authenticated authority/risk appetite, privileged DB posture, off-host backups/restore scheduling, monitoring/incident response and any private import remain separately human-owned D2 conditions. No legal/license adjudication or unrestricted production maturity is claimed.

Recommended next permitted action: strategic bounded D0 repair orders grounded in F1/F2/F3, preserving source/history/ownership boundaries; after their accepted merge, a fresh full architecture-to-current-main audit at the new exact revision. This report is read-only evidence and supplies no merge, release/exposure or CRITICAL-adjudication authority.
